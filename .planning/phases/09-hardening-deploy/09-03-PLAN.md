  <files>docs/ops-runbook.md</files>
  <action>
    Create `docs/ops-runbook.md`. The docs/ directory is at the repo root (same level as backend/).

    The runbook must cover two areas:

    **Section 1: Railway Volume Persistence Verification (NFR-5)**
    Manual checklist run after any forced Railway service restart or deploy:

    1. Trigger a restart: In the Railway dashboard, navigate to the fastapi service and
       click "Restart". Alternatively: `railway run --service fastapi -- echo restart` or
       use Railway's "Redeploy" button.
    2. Watch startup logs: In Railway logs for the fastapi service, confirm the line
       `INFO  [alembic.runtime.migration] Running upgrade ...` appears (Alembic runs on startup).
       If no migration output appears, check that the startup command includes alembic upgrade head
       or that the lifespan event triggers it.
    3. Verify rows survived: After restart completes (health check at /health returns 200),
       connect to the Railway PostgreSQL service and run:
       ```sql
       SELECT COUNT(*) FROM earnings_events;
       SELECT COUNT(*) FROM signals;
       SELECT COUNT(*) FROM alerts;
       SELECT COUNT(*) FROM portfolio_positions;
       ```
       Row counts must be non-zero and match pre-restart counts.
    4. Verify volume mount: In Railway service settings for fastapi, confirm the volume is
       mounted at /data (or the configured mount path). If rows are missing post-restart, the
       volume may be unmounted or the DATABASE_URL may point to a different instance.
    5. Pass criteria: All row counts match, /health returns 200, alembic upgrade head appears
       in startup logs.

    **Section 2: Production Smoke Test (post-deploy verification)**
    Run after every deploy to main:

    1. Health check:
       ```
       curl -f https://<RAILWAY_DOMAIN>/health
       # Expected: {"status": "ok"} HTTP 200
       ```
    2. Dashboard endpoint:
       ```
       curl -f https://<RAILWAY_DOMAIN>/api/v1/dashboard
       # Expected: JSON object with nav, daily_pnl, active_positions, macro_gate_status, recent_alerts
       # HTTP 200
       ```
    3. SSE stream connection:
       ```
       curl -N --max-time 5 https://<RAILWAY_DOMAIN>/api/v1/events
       # Expected: one or more ": heartbeat" lines within 30 seconds
       # HTTP 200 with Content-Type: text/event-stream
       ```
    4. Signal feed:
       ```
       curl -f https://<RAILWAY_DOMAIN>/api/v1/signals?limit=5
       # Expected: JSON array (may be empty if no signals yet) HTTP 200
       ```
    5. Alerts endpoint:
       ```
       curl -f https://<RAILWAY_DOMAIN>/api/v1/alerts?limit=5
       # Expected: JSON array HTTP 200
       ```
    6. Pass criteria: All 5 endpoints return HTTP 200. SSE stream opens and emits at least
       one heartbeat within 30 seconds.

    **Section 3: RL Trainer Manual Deploy**
    The rl_trainer service is excluded from auto-deploy (see cd.yml). To deploy manually:
    ```
    railway up --service rl_trainer
    ```
    Or use the Railway dashboard: navigate to rl_trainer service -> Deploy -> Manual Deploy.
    Warning: Do NOT add rl_trainer to the cd.yml deploy step. The test_deploy_gate.py CI test
    will fail if rl_trainer appears in any `railway up` command in cd.yml.

    **Section 4: Rollback Procedure**
    If a deploy causes errors:
    1. In Railway dashboard: navigate to the affected service -> Deployments -> select previous
       deployment -> click "Rollback".
    2. Or: `git revert HEAD && git push origin main` to trigger a new deploy with the revert.
    3. Database migrations: Alembic downgrade is available but requires manual intervention.
       Run `railway run --service fastapi -- alembic downgrade -1` to roll back one migration.

    Format: clear markdown with numbered steps, code blocks for commands, pass/fail criteria
    for each checklist item. No emojis.
